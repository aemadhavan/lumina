# DESIGN.md — LUMINA

## Components

LUMINA is structured as a decoupled multi-service system comprising a client presentation tier, an edge reverse-proxy gateway, an isolated AI agent core, an asynchronous document worker, and managed data stores. 
1. **Web UI (`web/`)**: A single-page application built on React 18, Vite, and Tailwind CSS. It runs in the user's browser (or is statically served from Vercel / edge gateway) and communicates exclusively with the Edge Gateway. It renders the query input, quick/deep gear toggles, streaming token feeds, interactive citation cards, and the `/evals` verification dashboard.
2. **Edge Gateway (`backend/gateway/`)**: An Express-based reverse proxy running on port `8787` (Fly.io / serverless in production). It handles edge concerns: CORS, `X-User-Id` authentication validation, inbound schema validation using Zod (`@lumina/contract`), client rate limiting (`RATE_LIMIT_PER_MINUTE=30`), unbuffered Server-Sent Events (SSE) streaming pass-through, and static hosting of production assets (`web/dist`).
3. **Agent Service (`backend/agent/`)**: A private, non-public Express AI service on port `8000`. It executes the core agentic reasoning loop (`quick` vs `deep` gears), enforces budget caps (quick: 8 calls / 90s, deep: 24 calls / 240s), runs tools (`web_search`, `fetch_page`, `save_memory`, `recall_memory`), handles thread memory injection, and manages RAG retrieval.
4. **Asynchronous Background Worker (`backend/agent/src/worker.ts`)**: A crash-safe Node.js process that polls the `jobs` collection in MongoDB Atlas. It handles multi-stage document ingestion: claiming queued file uploads, extracting text/pages from GridFS PDFs, chunking text with precise locators (`p. N`), generating 1536-dimensional embeddings, and writing to the vector store with read-your-write probes.
5. **MongoDB Atlas (`lumina` database)**: Authoritative cloud datastore hosting document collections (`threads`, `messages`, `memories`, `spaces`, `documents`, `chunks`, `jobs`, `searchCache`) and GridFS buckets (`fs.files`, `fs.chunks`) for PDF storage.
6. **Search Cache**: A two-tier caching hierarchy combining an in-process LRU cache (tier 1) for sub-millisecond repeated queries with a MongoDB TTL collection `searchCache` (tier 2, 24-hour TTL) keyed by SHA-256 of `(normalized query, provider)`.
7. **Run Logs (`runs/<requestId>.json`)**: Local append-only disk records capturing every query's full trajectory, tokens in/out, latency, server-side calculated costs, and ordered tool calls evaluated by `quality/check.mjs`.

## Responsibilities

Strict security and architectural isolation boundaries divide each component to eliminate secret leakage, prevent denial-of-service, and enforce single responsibility:
- **Gateway Exclusions**: The Gateway is the **only** component permitted to interact directly with the client browser and the only component that enforces `X-User-Id` existence and client-side rate limits. Conversely, the Gateway is strictly **forbidden** from possessing provider credentials (`ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, `OPENAI_API_KEY`, `TAVILY_API_KEY`, `MONGODB_URI`), executing agent tools, connecting to MongoDB, or making LLM requests.
- **Agent Service Exclusions**: The Agent Service is the **only** component permitted to hold provider API secrets, connect to MongoDB Atlas, call external model/search APIs, execute tools, and determine run budget termination (`cap` vs `done`). It is strictly **forbidden** from exposing public ports to the open internet; it listens solely on an internal private network or localhost, accessible exclusively via the Gateway proxy.
- **Background Worker Exclusions**: The Background Worker is the **only** component that parses heavy PDF documents and computes batch vector embeddings. It never handles client HTTP requests or answers real-time user search queries.
- **Web UI Exclusions**: The React Web UI is purely a presentation layer. It possesses zero access to backend secrets, holds no database drivers, and performs no server-side business logic. If inspected via browser developer tools, zero API keys or MongoDB URIs exist in the compiled bundle.

## Communication

Components interact via purpose-built synchronous and asynchronous protocols designed for sub-second first-paint latencies and resilience against upstream network degradation:
- **Browser ↔ Gateway**: Client-initiated HTTP POST for queries (`/threads/:id/ask`), thread lifecycle, and multipart file uploads (`/spaces/:id/documents`). For streaming queries, communication transitions to Server-Sent Events (SSE) over `text/event-stream`.
- **Gateway ↔ Agent**: Transparent HTTP reverse proxying. On `/threads/:id/ask`, the Gateway pipes the chunked SSE stream unbuffered from the Agent to the browser, transmitting `trace` $\rightarrow$ `sources` $\rightarrow$ `token` $\rightarrow$ `done` events with zero buffering to guarantee sub-2500ms TTFT. If the Agent service is unreachable or crashes during generation, the Gateway aborts the stream and terminates the HTTP connection with a clean `502 Bad Gateway` error.
- **Agent ↔ External Providers (LLM / Search)**: HTTPS REST calls to Google Gemini / Anthropic and Tavily API. All provider calls are bounded by network timeouts and adhere to a strict **"fail-loud"** contract: upstream timeouts or provider exceptions immediately terminate the run with `{ terminated: "error" }` and surface a 502, never swallowing exceptions to serve plausible hallucinations or empty results.
- **Agent ↔ Background Worker**: Asynchronous message passing mediated entirely through the MongoDB `jobs` collection. When a document is uploaded, the Agent writes the raw file to GridFS, inserts a `pending` job document, and responds immediately with `202 Accepted` (< 300ms). The worker polls for `pending` jobs, claims them using atomic `findAndModify` with a lease heartbeat (`claimedAt`), and processes them in the background.

## State

State within LUMINA is partitioned into authoritative persistent state, transient worker state, and ephemeral caches to guarantee zero data corruption and deterministic recovery:
- **Authoritative State (MongoDB Atlas)**: MongoDB is the single source of truth. All user conversation history (`threads`, `messages`), spaces and document metadata (`spaces`, `documents`), searchable text chunks (`chunks`), long-term semantic preferences (`memories`), and raw binary files (GridFS) reside authoritatively in MongoDB.
- **Ephemeral State (Caches)**: The in-process LRU cache and the MongoDB `searchCache` collection (with a 24-hour TTL index on `expiresAt`) are entirely ephemeral. If flushed or dropped at any moment, the system remains 100% operational, incurring only temporary external search latency while rebuilding.
- **Consistency Story for Ingested Documents**: Document processing is asynchronous and staged (`pending` $\rightarrow$ `parsing` $\rightarrow$ `chunking` $\rightarrow$ `embedding` $\rightarrow$ `indexing` $\rightarrow$ `indexed`). A document is **not** queryable simply because its chunks are upserted into the `chunks` collection. Because MongoDB Atlas Vector Search indexes have asynchronous build lag, a document transitions to `indexed` status **only after a read-your-write probe** successfully queries Atlas Vector Search and returns at least one of the newly written chunk IDs. If a worker process crashes mid-ingest, a sweeper detects stale `claimedAt` timestamps (> 5 minutes) and safely resets uncompleted jobs to `pending`.

## Trade-offs

During the design of LUMINA, four deliberate architectural trade-offs were chosen:
1. **MongoDB Atlas Vector Search vs. Dedicated Vector Store (e.g. Qdrant / Pinecone)**: We chose native Atlas Vector Search (`$vectorSearch`) to consolidate operational state, relational document metadata, conversation threads, and vector embeddings within a single ACID-compliant database. This completely eliminates multi-database synchronization lag, distributed transaction failures, and dual-store maintenance. The trade-off is accepting the strict free-tier limit of 3 search indexes per cluster on Atlas M0, as well as an unavoidable asynchronous index synchronization latency following chunk upserts.
2. **In-Process LRU + MongoDB TTL vs. Standalone Redis Cache**: We implemented a hybrid two-tier cache (local memory LRU backed by MongoDB `searchCache` with TTL) instead of running a dedicated Redis instance. This choice eliminates external operational dependencies, reduces hosting infrastructure costs, and provides sub-microsecond in-memory lookups for hot search queries. The trade-off is that multiple horizontally-scaled agent replicas do not share an in-memory tier, relying on the MongoDB second tier for cache synchronization across nodes.
3. **Deterministic Single-Agent Loop vs. Multi-Agent Swarm / Orchestrator**: We chose a single iterative agent loop bounded by strict caps (quick: 8 tool calls / 90s, deep: 24 tool calls / 240s) rather than a complex multi-agent hierarchical swarm. This provides absolute determinism, predictable per-query latency, low token overhead, and guaranteed adherence to SLA benchmarks. The trade-off is sacrificing isolated persona specialization and parallel non-linear exploration.
4. **GridFS & Polled MongoDB Queue vs. AWS S3 + SQS**: We chose MongoDB GridFS and collection-based job leasing over AWS S3 and SQS. This keeps document RAG fully self-contained within the database cluster with zero cloud provider lock-in, enabling simple local and multi-cloud deployment. The trade-off is that polling the `jobs` collection introduces periodic query overhead and lacks the millisecond push latency and infinite scale of dedicated cloud queue primitives.
